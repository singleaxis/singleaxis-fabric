# Host records and host vectors (spec 053 §6.2; spec 056 M2)

Generated by `scripts/contracts/generate_p0_contracts.py` from
`scripts/contracts/host_records.py`, which is also the executable form of the rules
below; `scripts/contracts/validate_capture_contracts.py` recomputes every document. No
sensor emits these records yet: the host-records library (WP4-07a), the auditd receiver
(WP4-07b) and the eBPF emitter (WP4-07c) must produce this shape, and fabricguard's host
admission (WP4-08b) must give each batch's expected result.

## A host-record fixture

```text
{schema_version: "fabric.host-record-fixture/v1", name, description, key,
 guard:    {source_kind, profile, tenant_id, source_id, host_digests},
 batches:  [OTLP/JSON ExportTraceServiceRequest, ...],   # ptrace.JSONUnmarshaler reads them
 expected: [{spans: [{name, attributes}], stripped: {key: count}, dropped: n}, ...]}
```

`guard` is the receiving `fabricguard/<group>` instance (056 §7.3.3 (e)). Attributes are
OTLP key-value lists, so a repeated key can be expressed. A valid fixture carries the
admission of each batch; a refused one carries none and fails with its code.

## Admission (spec 053 §6.2.7), as `host_records.admit` applies it

1. A repeated key in any span refuses the batch (`capture.host.repeated_key`).
2. A supplied `fabric.source.authenticated` is removed.
3. (Log records: a host group has none; not in these fixtures.)
4. Each span is a host record (records class, capture point of kind S), a manifest, a
   `periodic` or `final` heartbeat, or a loss marker; anything else (an agent record, an
   exchange, a run marker, a seal) refuses the whole batch
   (`capture.host.not_host_evidence`).
5. `fabric.tenant_id` and `fabric.source_id` equal the binding, the capture point id
   equals `source_kind`, and a manifest's rows name only `source_kind`; otherwise the batch
   is refused (`capture.host.binding`).
6. Keys outside the host placement are stripped and counted: for a host record the
   053 §6.2.3 keys (`records-span-v1.json` `host_placement`), for a marker its registry
   placement plus the spec 047 marker keys. A missing or failing identity, capture or
   sequence key drops the span and counts it; so does a syscall of another event class.
7. Digest keys are stripped unless `host_digests: permitted`.
8. `fabric.source.authenticated=true` is stamped.

An `agent` instance refuses any span of a kind-S capture point and any `fabric.sensor.*`
key (`capture.host.sensor_on_agent`). A `source_kind` outside `agent`, `host.auditd`,
`host.ebpf` is refused (`capture.host.source_kind`). Across batches, a position seen again
with another event id is a replay that minted new ids (`capture.host.replay`); the
verifier reports it as a `sequence_conflict`.

## Decisions where spec 053 is silent or loose

- **Digest values are bare hex.** 053 §6.2.3 writes `sha256:` + 64 hex for
  `fabric.sensor.{exe,argv,path}_sha256`, but fabricguard strips any value of a key
  ending in `sha256` that is not bare 64 hex (the Node hash-key rule, as for today's
  local-profile digests). The registry rows use bare hex.
- **The manifest is a capture-manifest-v1 document** with `sdk.language: go` (the
  host-records library) and the disabled event classes as `sensor_exec`,
  `sensor_connect`, `sensor_file` in `uncaptured_classes`: two additive enum values of
  the manifest schema, because a host source's manifest could not be valid otherwise.
- **Markers carry `fabric.capture.point`** (their registry placement allows it), so
  step 5 can check every span's kind; host records carry `fabric.tenant_id`, a records
  key only on a capture point of kind S.
- **Upstream loss keys ride `periodic` heartbeats** (the registry has no `heartbeat`
  placement; 053 §6.2.4 reports loss "on the next periodic heartbeat").
